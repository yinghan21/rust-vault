# 异步编程

> [!abstract] 一句话
> `async fn` 只是返回一个**还没开始运行**的 `Future`；必须有 executor（如 tokio）反复 `poll` 到 `Poll::Ready`，函数体里的事情才真的发生。

## 为什么需要它

一个线程默认要几 MB 栈，切换由内核完成；一万个并发连接就想开一万个线程，内存和调度开销都撑不住。async 把「等 I/O」变成可以在用户态暂停的函数状态机：一个线程能同时推进上万个任务，暂停时只占几百字节。

代价是**协作式**：没人轮询，`Future` 一步也不动。标准库只提供到 [[pin|std::pin]] 与 [[task|std::task]] 为止的零件，执行器要自己选——生态里最常用的是 tokio（见 [[27-常用 crate 与生态|常用 crate 与生态]]）。

## async/await 是语法糖

- `async fn foo() -> T` 等价于 `fn foo() -> impl Future<Output = T>`；调用它**不会执行函数体**，只造出一个 Future。
- 函数体被编译器改写成状态机，每个 `.await` 是一个可暂停的断点：返回 `Pending` 就把控制权交还 executor，下次被 poll 时从断点继续。
- `.await` 只能出现在 `async` 上下文（`async fn` 或 `async {}` 块）里；它不阻塞线程，只是「让出」。

## Future 与 poll 模型

`Future` 只有一个方法：`poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>`。返回 `Ready(值)` 表示完成，`Pending` 表示「还没好，等我通过 `cx.waker()` 叫你再轮询」。`Pin` 的原因很实在：状态机里存着跨 `await` 的局部变量，Future 一旦被 poll 过就不能再被移动，否则自引用指针会悬空。

下面用标准库零件手搓一个执行器，看清 `poll` 到底是怎么被驱动的。

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll, Waker};

/// 最简单的 Future：poll 一次就交出结果
struct Immediate(i32);

impl Future for Immediate {
    type Output = i32;
    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<i32> {
        Poll::Ready(self.0)
    }
}

/// 极简 executor：循环 poll，直到 Ready
fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = Box::pin(fut); // 钉在堆上，地址不再变化
    let mut cx = Context::from_waker(Waker::noop());
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => std::thread::yield_now(), // 真实运行时在这里挂起线程
        }
    }
}

fn main() {
    assert_eq!(block_on(Immediate(40 + 2)), 42);
    // async 块本身就是 Future：语法糖最终落到同一个 trait 方法上
    assert_eq!(block_on(async { (1..=4).sum::<i32>() }), 10);
}
```

## executor 的职责

executor（也叫运行时）做三件事：**保存任务**（每个 `spawn` 的 Future 变成一个可调度的任务）、**轮询**（就绪队列里逐个 poll）、**唤醒**（把 `Waker` 交给 I/O 驱动，epoll/kqueue 事件到达时把任务重新入队）。真实实现不会像上面那样忙等，而是在 `Pending` 时睡在事件循环上，所以 CPU 占用接近零。

这也解释了一个常见误解：`async` 不会自动并行。任务只在 `.await` 处交替执行；`#[tokio::main]` 默认起多线程运行时，但单个任务内部仍是串行的。

## tokio 入门

tokio 是最主流的异步运行时。它不是标准库的一部分，**必须作为依赖引入**，见下方示例首行的 `Cargo.toml` 注记。

```rust
// Cargo.toml: tokio = { version = "1", features = ["full"] }
use std::time::Duration;

#[tokio::main] // 展开成启动运行时 + block_on(async { ... })
async fn main() {
    let h = tokio::spawn(async {
        tokio::time::sleep(Duration::from_millis(50)).await;
        21
    });

    println!("主任务不阻塞");
    assert_eq!(h.await.unwrap(), 21); // JoinHandle 也是 Future
}
```

> [!warning] tokio 示例不能用 `rustc` 直接编译
> 上面和下面这些 tokio 示例都依赖 crate 与 `#[tokio::main]` 宏展开，必须 `cargo new` 建项目、在 `Cargo.toml` 写入依赖后 `cargo run`。直接用 `rustc` 编译会报「can't find crate for `tokio`」。

`tokio::join!` 并发等待多个 Future（同一个任务内交替推进、全部完成才继续），`tokio::select!` 则在多个分支里**谁先就绪走谁**、其余分支被取消：

```rust
// Cargo.toml: tokio = { version = "1", features = ["full"] }
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    // join!：不创建新任务，只是把多个 Future 放在一起轮询
    tokio::join!(
        sleep(Duration::from_millis(10)),
        sleep(Duration::from_millis(20))
    );
    println!("两个等待都结束了");

    // select!：谁先完成走谁，其余分支立刻被丢弃
    let mut got = 0;
    tokio::select! {
        _ = sleep(Duration::from_secs(1)) => println!("1 秒到"),
        v = async { 7 } => got = v,
    }
    assert_eq!(got, 7);
}
```

## 与线程模型的对比

| 维度 | 线程（[[21-并发编程|并发编程]]） | async |
| --- | --- | --- |
| 调度 | 内核抢占式 | 用户态协作式，只在 `.await` 让出 |
| 单个开销 | 栈 MB 级，切换要进内核 | 任务几百字节，切换是一次函数返回 |
| 适合 | CPU 密集、少量连接 | 高并发 I/O、大量等待 |
| 阻塞调用 | 天经地义 | 会卡住整个执行器 |
| 依赖 | 标准库 | 需要第三方运行时 |

## 常见坑

| 坑 | 现象 | 对策 |
| --- | --- | --- |
| 在 `async` 里调阻塞函数 | 同一线程上所有任务一起饿死 | `tokio::task::spawn_blocking` 或换异步 API |
| 跨 `.await` 持 `std` 的 `MutexGuard` | `E0277`：guard 不是 `Send` | 先把 guard `drop` 掉，或换 `tokio::sync::Mutex` |
| 对 `Future` 取引用并移动 | `E0277`：Future 不满足 `Unpin` | `Box::pin`、`tokio::pin!` 或 `Pin::new` |
| 忘了 `Send` 边界 | `spawn` 要求 `F: Send + 'static` | 别把 `Rc`/`RefCell` 带进 `spawn` 的 Future |
| 直接 `rustc` 编译 tokio 示例 | `can't find crate for tokio` | 建 cargo 项目，写 `Cargo.toml` |
