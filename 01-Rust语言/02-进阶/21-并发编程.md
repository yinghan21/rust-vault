# 并发编程

> [!abstract] 一句话
> Rust 的并发安全不靠库约定，而靠 `Send`/`Sync` 两个标记特质：跨线程不安全的类型直接编译不过，数据竞争在 `unsafe` 之外不可能发生。

## 为什么需要它

C/C++ 的数据竞争是未定义行为，只能靠人眼和 sanitizer 抓；Java 靠 `synchronized` 自觉；Python 有 GIL，多线程只是假并行。Rust 走**无畏并发**：把所有权与借用规则扩展到线程之间，编译期挡掉竞争，运行时既没有 GC 也没有全局锁。常用手段有三种——消息传递（`mpsc` 通道）、共享内存（`Arc<Mutex<T>>`、`Arc<RwLock<T>>`）、原子操作（`AtomicUsize`）。

## 创建线程：`spawn`、`join` 与 `move`

`thread::spawn` 接收闭包、返回 `JoinHandle<T>`，`join()` 阻塞等待并取回 `Result`（`Err` 表示子线程 panic）。闭包默认按需借用，但子线程可能活到外层函数返回之后，编译器给不出足够长的生命周期（`E0373`），所以通常要加 `move` 把变量移入闭包。

```rust
use std::thread;

fn main() {
    let handle = thread::spawn(|| (1..=100).sum::<i32>());
    assert_eq!(handle.join().unwrap(), 5050);
    let data = vec![1, 2, 3];
    let h2 = thread::spawn(move || data.iter().sum::<i32>()); // move 移入线程
    // println!("{:?}", data); // ❌ E0382：data 已被移入线程
    assert_eq!(h2.join().unwrap(), 6);
}
```

进程退出不会等待没 `join` 的线程：要么 `join`，要么丢掉 handle 并接受结果被忽略。要共享只读数据就 `clone()`，或用 [[20-智能指针|智能指针]] 里的 `Arc`。

## `thread::scope`：借用局部变量

Rust 1.63 起有作用域线程：`scope` 保证内部 `spawn` 的线程在闭包结束前全部 `join`，因此能直接借用栈上数据，不必 `move`、也不必 `Arc`。

```rust
use std::thread;

fn main() {
    let mut data = vec![1, 2, 3];
    thread::scope(|s| {
        let h = s.spawn(|| data.iter().sum::<i32>()); // 借用栈上的 data，不移动
        assert_eq!(h.join().unwrap(), 6);
    }); // 所有作用域线程都已结束
    data.push(4); // 借用结束后又能可变借用
    assert_eq!(data.len(), 4);
}
```

## `mpsc` 通道：单生产者多消费者

`mpsc` = multi-producer, single-consumer：`Sender` 能 `clone` 出多个生产者，`Receiver` 只有一个消费者。所有 `Sender` 被丢弃后 `rx.iter()` 自然结束，所以别忘了 `drop(tx)`。

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for id in 0..3 {
        let tx = tx.clone(); // 每个线程一个发送端
        thread::spawn(move || tx.send(format!("线程{id}完成")).unwrap());
    }
    drop(tx); // 丢掉原始 tx，否则 rx 永远等不到结束
    let mut msgs: Vec<String> = rx.iter().collect();
    assert_eq!(msgs.len(), 3);
    println!("{msgs:?}");
}
```

## `Arc<Mutex<T>>`：共享可变状态

`Arc` 提供多所有者，`Mutex` 保证同一时刻只有一个写者。`lock()` 返回 `MutexGuard`，离开作用域自动解锁；返回 `Err` 表示持锁线程 panic 过（锁中毒）。

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut hs = Vec::new();
    for _ in 0..10 {
        let counter = Arc::clone(&counter); // 只复制指针并原子加一
        hs.push(thread::spawn(move || *counter.lock().unwrap() += 1));
    }
    for h in hs {
        h.join().unwrap();
    }
    assert_eq!(*counter.lock().unwrap(), 10);
}
```

## `RwLock` 与原子类型

`RwLock<T>` 适合读多写少：`read()` 可同时多个、`write()` 独占，临界区很细时未必比 `Mutex` 快，先量测再换。`AtomicUsize`/`AtomicBool` 则在单个机器字上做原子读改写，没有锁也不阻塞线程；`Ordering` 决定内存序——入门一律 `SeqCst`，只求原子性、不关心重排时用 `Relaxed`。

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let hits = Arc::new(AtomicUsize::new(0));
    let mut hs = Vec::new();
    for _ in 0..4 {
        let hits = Arc::clone(&hits);
        hs.push(thread::spawn(move || (0..100).for_each(|_| {
            hits.fetch_add(1, Ordering::Relaxed); // 不会丢更新
        })));
    }
    for h in hs { h.join().unwrap(); }
    assert_eq!(hits.load(Ordering::SeqCst), 400);
}
```

## `Send` 与 `Sync` 的含义

- `Send`：值可以把所有权**转移**到另一个线程；`Sync`：`&T` 可同时被多个线程持有（等价于 `&T: Send`）。

编译器按字段自动推导：字段全 `Send` 的结构体就 `Send`。`Rc`、`RefCell`、裸指针都不满足，`Arc<Mutex<T>>` 在 `T: Send` 时满足；给自定义类型写 `unsafe impl Send`，等于向编译器承诺内部不变量由你手工维护。

## 死锁与锁粒度

死锁的经典成因是加锁顺序不一致：线程 A 持 `m1` 等 `m2`，线程 B 持 `m2` 等 `m1`。对策是固定全局加锁顺序、用 `try_lock` 加超时、或把两把锁合并成一把。锁粒度两头都要防：临界区太大等于串行，太小则加锁开销盖过收益——原则是**先取数据、再计算，只在写回时短暂持锁**，且绝不在持锁期间做 I/O 或调用可能 panic 的代码（panic 会毒化锁，之后 `lock()` 全部返回 `Err`）。

## 常见错误与解决

| 错误 | 原因 | 解决 |
| --- | --- | --- |
| `E0373: closure may outlive` | 闭包借用了局部变量 | 加 `move` 或用 `thread::scope` |
| `E0277: Rc<i32> cannot be sent` | `Rc` 不是 `Send` | 换成 `Arc` |
| `E0382: use of moved value` | `move` 之后原变量失效 | 提前 `clone()` |
| `rx.iter()` 一直不结束 | 还有 `Sender` 存活 | `drop(tx)` |
| 计数偶尔少加一次 | 忘了 `lock()` 或非原子读改写 | 所有访问都走 `Mutex` 或原子 API |
