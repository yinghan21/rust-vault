# 集合类型

> [!abstract] 一句话
> 标准库的集合全部是泛型容器：`Vec` 管顺序，`HashMap`/`BTreeMap` 管键值，`HashSet`/`BTreeSet` 管去重，`VecDeque` 管两端，`BinaryHeap` 管优先级；先选结构，再谈性能。

## 为什么需要它

C 里动态数组要手写 `realloc`，哈希表得自己找库；C++ 的 STL 容器很全，但每个容器的接口各写一套，`std::map` 和 `std::unordered_map` 的迭代器行为还不一样；Python 的 `list`/`dict` 好用，但只有两三种结构，双向队列得靠 `collections.deque`。

Rust 的做法是：结构数量克制，接口靠 trait 统一——`Iterator`、`FromIterator`、`Extend`、`Index`、`Entry` 让所有容器用起来手感一致。`Vec` 和 `HashMap` 通过 prelude 直接可用，其余要 `use std::collections::...`（[[collections|std::collections]]）。

## 先看选型表

| 需求 | 选 | 一句话理由 |
| --- | --- | --- |
| 连续存储、按下标访问、末尾增删 | `Vec<T>` | 缓存友好，绝大多数场景的默认答案 |
| 键值查找，不关心顺序 | `HashMap<K, V>` | 平均 O(1)，最快 |
| 键值查找，还要按 key 有序或范围查询 | `BTreeMap<K, V>` | 有序遍历、`range` 开箱即用 |
| 只要去重 / 集合运算 | `HashSet<T>` | 平均 O(1) 的 `contains` |
| 去重且要按序输出 | `BTreeSet<T>` | 迭代顺序稳定，测试友好 |
| 两端都要 push/pop | `VecDeque<T>` | 头尾都是 O(1)，`Vec` 头部插入是 O(n) |
| 每次取最大/最小值 | `BinaryHeap<T>` | 堆顶 O(1)，适合 Top-K、任务调度 |

## capacity 与扩容

`Vec` 内部是「指针 + len + capacity」：`len` 是已有元素个数，`capacity` 是不重新分配就能容纳的个数。`push` 超过容量时会重新分配一块更大的内存、把旧元素搬过去，通常是翻倍（属于实现细节，不保证）。

推论：已知规模就用 `with_capacity` 预分配，避免边 push 边搬家；一次性建好不再增删时用 `shrink_to_fit` 把多余内存还回去。

```rust
fn main() {
    let mut v: Vec<i32> = Vec::with_capacity(4);
    assert_eq!(v.len(), 0);
    assert_eq!(v.capacity(), 4);

    for i in 0..4 {
        v.push(i);
    }
    assert_eq!(v.capacity(), 4); // 正好填满，没有扩容

    v.push(4); // 触发扩容
    assert!(v.capacity() >= 5);
    assert_eq!(v.len(), 5);

    v.shrink_to_fit();
    assert!(v.capacity() >= v.len());
    println!("len = {}, capacity = {}", v.len(), v.capacity());
}
```

## entry API：一次查表搞定「查不到就插入」

先 `get` 再 `insert` 会查两次表，而且借用检查器常常不让过。`entry` 把「查」和「写」合成一个入口：`or_insert` 在空缺处插入默认值并返回 `&mut V`，拿到就能直接改。

```rust
use std::collections::HashMap;

fn main() {
    let text = "a b a c b a";
    let mut counts: HashMap<&str, u32> = HashMap::new();

    for word in text.split_whitespace() {
        // 键不存在就插入 0，然后对返回的 &mut u32 自增
        *counts.entry(word).or_insert(0) += 1;
    }
    assert_eq!(counts["a"], 3);
    assert_eq!(counts.get("b"), Some(&2));
    assert_eq!(counts.get("z"), None);

    // 命中就先改，没命中再插
    counts.entry("d").and_modify(|c| *c += 10).or_insert(1);
    assert_eq!(counts["d"], 1);

    // 默认值构造有开销时用 or_insert_with，避免每次白算
    counts.entry("e").or_insert_with(|| "e".len() as u32);
    assert_eq!(counts["e"], 1);
    println!("{:?}", counts);
}
```

## 三种迭代方式

这是集合最容易踩坑的地方，区别只在于「拿到的是什么」：

| 写法 | 元素类型 | 集合之后还能用吗 |
| --- | --- | --- |
| `iter()` | `&T` | 能，只读借用 |
| `iter_mut()` | `&mut T` | 能，可变借用 |
| `into_iter()` | `T` | 不能，所有权被移走 |

`for x in &v`、`for x in &mut v`、`for x in v` 分别等价于上面三种。

```rust
fn main() {
    let mut v = vec![1, 2, 3];

    // 1. iter()：只读借用
    let sum: i32 = v.iter().sum();
    assert_eq!(sum, 6);

    // 2. iter_mut()：可变借用，可以原地修改
    for x in v.iter_mut() {
        *x *= 10;
    }
    assert_eq!(v, vec![10, 20, 30]);

    // 3. into_iter()：消耗集合，元素所有权归迭代器
    let moved: Vec<i32> = v.into_iter().map(|x| x + 1).collect();
    assert_eq!(moved, vec![11, 21, 31]);
    // println!("{:?}", v); // 取消注释会报错：v 已被移动到迭代器里
}
```

## 其余容器的常用姿势

```rust
use std::cmp::Reverse;
use std::collections::{BTreeMap, BTreeSet, BinaryHeap, HashSet, VecDeque};

fn main() {
    // VecDeque：头尾进出都是 O(1)
    let mut q: VecDeque<i32> = VecDeque::new();
    q.push_back(2);
    q.push_front(1);
    assert_eq!(q.pop_front(), Some(1));
    assert_eq!(q.pop_back(), Some(2));

    // BinaryHeap：默认是最大堆
    let mut heap = BinaryHeap::from(vec![3, 1, 5]);
    assert_eq!(heap.peek(), Some(&5));
    assert_eq!(heap.pop(), Some(5));

    // 套一层 Reverse 就变成最小堆
    let mut min_heap: BinaryHeap<Reverse<i32>> = BinaryHeap::new();
    min_heap.push(Reverse(3));
    min_heap.push(Reverse(1));
    assert_eq!(min_heap.pop(), Some(Reverse(1)));

    // HashSet：去重与集合运算
    let a: HashSet<i32> = [1, 2, 3].into_iter().collect();
    let b: HashSet<i32> = [3, 4].into_iter().collect();
    assert_eq!(a.intersection(&b).count(), 1);
    assert_eq!(a.union(&b).count(), 4);

    // BTreeSet：迭代顺序天然有序，测试里很省心
    let names: BTreeSet<&str> = ["carol", "alice", "bob"].into_iter().collect();
    assert_eq!(names.iter().next(), Some(&"alice"));

    // BTreeMap：按 key 有序，支持范围查询
    let mut score = BTreeMap::new();
    score.insert("bob", 80);
    score.insert("alice", 90);
    score.insert("carol", 70);
    let top: Vec<&str> = score.range("a"..="b").map(|(k, _)| *k).collect();
    assert_eq!(top, vec!["alice", "bob"]);
    println!("容量与结构演示完成");
}
```

## 性能对比

下表的 n 是元素个数，哈希行的复杂度是**平均**情况（最坏会退化到 O(n)）：

| 容器 | 查找 | 插入 | 删除 | 有序遍历 | 主要代价 |
| --- | --- | --- | --- | --- | --- |
| `Vec` | O(1) 下标 / O(n) 按值 | 末尾 O(1) 均摊 | O(n) | 否 | 中间插删要搬元素 |
| `VecDeque` | O(n) | 两端 O(1) 均摊 | 两端 O(1) 均摊 | 否 | 内存不连续，不能直接切片 |
| `HashMap` | 平均 O(1) | 平均 O(1) | 平均 O(1) | 否 | SipHash 开销，顺序不保证 |
| `BTreeMap` | O(log n) | O(log n) | O(log n) | 是 | 常数比哈希大 |
| `HashSet` | 平均 O(1) | 平均 O(1) | 平均 O(1) | 否 | 同 `HashMap` |
| `BTreeSet` | O(log n) | O(log n) | O(log n) | 是 | 同 `BTreeMap` |
| `BinaryHeap` | 只看堆顶 O(1) | O(log n) | 出堆 O(log n) | 否 | 不能查找中间元素 |

两个补充：默认 `Hasher` 用 SipHash 抵御哈希洪水攻击，安全但比手写哈希慢，性能敏感时才考虑替换；`HashMap` 的迭代顺序每次运行都可能不同，任何依赖顺序的测试都该换成 `BTreeMap`/`BTreeSet` 或先排序。

## 常见错误与解决

| 错误 | 原因 | 解决 |
| --- | --- | --- |
| `index out of bounds` panic | `v[i]` 不做边界检查之外的兜底 | 用 `get(i)` 拿 `Option`，或 `get_mut` |
| 迭代时想修改集合，报借用冲突 | `iter()` 借了不可变引用 | 先 `collect` 出要改的键，或改用 `iter_mut()` |
| `the trait bound K: Hash + Eq is not satisfied` | 自定义 key 没派生 `Hash`/`Eq` | `#[derive(Hash, PartialEq, Eq)]`，或换 `BTreeMap`（只需 `Ord`） |
| 测试时顺序偶发不一致 | 哈希容器不保证顺序 | 换 `BTreeMap`/`BTreeSet`，或断言前先 `sort` |
| 大量 `push` 很慢 | 反复扩容搬数据 | `Vec::with_capacity(n)` 预分配 |
