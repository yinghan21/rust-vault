# 错误处理

> [!abstract] 一句话
> Rust 没有异常：能恢复的错误写在返回类型里（`Result<T, E>`），无法继续的错误才 `panic`；`?` 是「出错就提前返回，并顺手做一次错误类型转换」的语法糖。

## 为什么需要它

C 用返回值加 `errno`，调用方忘了检查就静默出错；Java 的受检异常强制处理，但 `catch` 一包就丢失了具体类型；Go 的 `if err != nil` 显式，但错误链和上下文全靠手工拼。

Rust 把「失败」变成**返回值的一部分**：函数签名 `-> Result<T, E>` 就在说「我可能失败，失败时给你 `E`」。不处理就拿到 `T` 不了，编译器会盯着你。`panic` 则留给「程序本身写错了」的情况，比如数组越界、断言失败（[[macro.panic|panic]]）。

## panic 与 Result 的边界

判断标准不是「错误严不严重」，而是「**调用方有没有可能合理地处理它**」。

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 文件不存在、解析失败、网络超时 | `Result` | 调用方可能重试、换路径、用默认值 |
| 用户输入非法（命令行参数、HTTP 请求体） | `Result` | 这是正常业务分支，不是 bug |
| 数组越界、整数溢出（debug 下）、`unreachable!()` | `panic` | 说明代码逻辑写错了 |
| 库内部的不变量被破坏 | `panic` | 继续跑只会产生更难查的错误 |
| 示例、测试、原型里的 `unwrap()` | `panic` | 目的是「错了我立刻知道」 |

两条实践原则：

- **库代码不要因为用户输入而 panic**，别人没法在你的库里 `catch`；把选择权交给调用方。
- `unwrap()` 不带信息，`expect("读取配置失败")` 至少能在 panic 消息里留下线索。正式代码里两个都该少用。

```rust
fn main() {
    // panic 不是「不可捕获的崩溃」：它先展开栈、跑析构，再终止线程
    let r = std::panic::catch_unwind(|| {
        let v = vec![1, 2, 3];
        v[10] // 越界访问触发 panic
    });
    assert!(r.is_err());
    println!("越界访问已经被拦截");
}
```

## ? 运算符与 From 转换

`expr?` 展开后大致等价于：

```text
match expr {
    Ok(v) => v,
    Err(e) => return Err(From::from(e)),
}
```

最后那个 `From::from` 是关键：**只要目标错误类型实现了 `From<源错误>`，`?` 就能自动转换**，不需要手写 `map_err`（[[convert.From|From]]）。

- 同一个函数里可以 `?` 不同来源的错误，前提是它们都能转成函数的错误类型。
- `Option` 也能用 `?`：`None` 时直接返回 `None`，但函数必须返回 `Option`。
- `Result` 函数里对 `Option` 用 `?` 不行，要先 `.ok_or(...)` / `.ok_or_else(...)` 转成 `Result`。

```rust
fn first_word_len(text: &str) -> Option<usize> {
    let word = text.split_whitespace().next()?; // None 就提前返回
    Some(word.len())
}

fn main() {
    assert_eq!(first_word_len("hello world"), Some(5));
    assert_eq!(first_word_len("   "), None);
    println!("first_word_len 正常");
}
```

## 自定义错误类型

库对外暴露的错误应该是一个**具体类型**：能 `match`、能加字段。它需要三样东西——`Debug`（便于打印和测试）、`Display`（给人看）、`Error`（接入错误链）。`source()` 用来说明「这个错误是不是由另一个错误引起的」。

```rust
use std::error::Error;
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    MissingKey(String),
    BadNumber(ParseIntError),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::MissingKey(key) => write!(f, "缺少配置项：{}", key),
            ConfigError::BadNumber(e) => write!(f, "数字格式错误：{}", e),
        }
    }
}

impl Error for ConfigError {
    // 底层原因，方便一层层回溯
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            ConfigError::MissingKey(_) => None,
            ConfigError::BadNumber(e) => Some(e),
        }
    }
}

// 有了这条，parse() 后面的 ? 才能自动转换错误类型
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::BadNumber(e)
    }
}

fn parse_port(text: &str) -> Result<u16, ConfigError> {
    let port: u16 = text.parse()?; // 出错时自动 From<ParseIntError>
    if port == 0 {
        return Err(ConfigError::MissingKey("port".to_string()));
    }
    Ok(port)
}

fn main() -> Result<(), Box<dyn Error>> {
    assert_eq!(parse_port("8080")?, 8080);

    let err = parse_port("abc").unwrap_err();
    assert!(err.source().is_some());
    println!("错误信息：{}", err);
    Ok(())
}
```

## Box\<dyn Error\>：写给 main 和脚本

`Box<dyn Error>` 意思是「任意一种错误的盒子」，适合 `main`、测试、一次性脚本——这些地方只关心「打印出来退出」，不关心具体类型。`?` 遇到任何实现了 `Error` 的类型都会自动装箱。

代价是丢掉了具体类型（要 `downcast` 才能拿回来）和一次堆分配，所以**公开 API 不要返回 `Box<dyn Error>`**。

```rust
use std::error::Error;

fn read_number(text: &str) -> Result<i32, Box<dyn Error>> {
    let n: i32 = text.trim().parse()?; // ParseIntError 自动装箱
    if n < 0 {
        return Err(format!("不能为负数：{}", n).into()); // String 也能装箱
    }
    Ok(n)
}

fn main() {
    assert_eq!(read_number(" 42 ").unwrap(), 42);
    assert!(read_number("-1").is_err());
    assert!(read_number("oops").is_err());
    println!("read_number 处理完毕");
}
```

## thiserror 与 anyhow 的定位

标准库这套已经够用，但样板代码多。社区的两个 crate 各管一边：

- `thiserror`：给**库**用。一个 derive 生成 `Display`、`Error`、`From` 的实现，错误类型仍然是具体的枚举，调用方照样能 `match`。相当于把上面手写的那几十行压缩成几个属性。
- `anyhow`：给**应用**用。`anyhow::Error` 是加强版 `Box<dyn Error>`，支持 `.context("读取配置")` 附加上下文、`?` 自动转换、打印时输出完整错误链。
- 共同点：都建立在 `std::error::Error` 之上。**先掌握标准库的写法**，理解 `From` 和 `source` 在做什么，再决定要不要引入依赖（[[27-常用 crate 与生态|常用 crate 与生态]]）。

## 常见错误与解决

| 错误 | 原因 | 解决 |
| --- | --- | --- |
| `the trait bound ... From<...> is not satisfied` | 目标错误类型没有 `From<源错误>` | 手写 `impl From`，或在调用处 `map_err` |
| `mismatched types`，期望 `Result` 却给了 `Option` | 两种「可能没有」混用 | 用 `ok_or` / `ok_or_else` 把 `Option` 转成 `Result` |
| `the trait bound E: Debug is not satisfied` | `unwrap`/`expect`/返回 `Result` 的 `main` 都要求 `E: Debug` | 给错误类型 `#[derive(Debug)]` |
| `?` 在返回 `Option` 的函数里用在 `Result` 上 | 两侧错误类型不同 | 统一函数返回类型，或改用 `ok()` |
| panic 消息看不出上下文 | 用了无信息的 `unwrap()` | 换 `expect("...")`，或干脆返回 `Result` |
