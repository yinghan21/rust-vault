# 常见陷阱

> [!abstract] 一句话
> 这些坑多数**能编译通过**：debug 与 release 行为不同、运行时 panic、逻辑静默出错，所以要在写的时候就避开。

## 1. 整数溢出：debug panic、release 环绕

| 项目 | 内容 |
| --- | --- |
| 现象 | debug 下 panic `attempt to add with overflow`，release 下悄悄变成 0 |
| 为什么 | release 默认 `overflow-checks = false`，溢出按二进制补码环绕 |
| 规避 | 明确用 `checked_*` / `saturating_*` / `wrapping_*` 表达意图 |

```rust
fn main() {
    let x: u8 = 255;
    println!("{:?}", x.checked_add(1)); // None，调用方必须处理
    println!("{}", x.saturating_add(1)); // 255，钉在上限
    println!("{}", x.wrapping_add(1)); // 0，显式环绕
}
```

## 2. 浮点比较：`==` 几乎总是错的

| 项目 | 内容 |
| --- | --- |
| 现象 | `0.1 + 0.2 == 0.3` 得到 `false` |
| 为什么 | 二进制浮点无法精确表示 0.1 这类十进制小数，累加会带舍入误差 |
| 规避 | 比较差值绝对值，或用整数分（比如以「分」代替「元」） |

```rust
fn main() {
    let sum: f64 = 0.1 + 0.2;
    println!("{}", sum == 0.3); // false
    println!("{}", (sum - 0.3).abs() < 1e-9); // true，按容差比较
}
```

另外 `f64` 不实现 `Ord`/`Eq`，所以不能用 `HashMap` 的默认键，也不能直接 `sort()`。

## 3. 字符串索引：`s[0]` 拿不到字符

| 项目 | 内容 |
| --- | --- |
| 现象 | `&s[0]` 编译不过（`str` 不能按索引取值），或 `s[0..1]` 运行时 panic |
| 为什么 | `String` 是 UTF-8 字节序列，索引返回字节区间，落在字符中间会 panic |
| 规避 | 用 `chars()` 迭代，或 `get(range)` 返回 `Option` 自行处理 |

```rust
fn main() {
    let s = "héllo"; // é 占两个字节
    println!("{}", s.len()); // 6 字节
    println!("{}", s.chars().count()); // 5 个字符
    match s.get(0..1) {
        Some(c) => println!("{:?}", c),
        None => println!("不在字符边界上"),
    }
}
```

## 4. 迭代器是惰性的

| 项目 | 内容 |
| --- | --- |
| 现象 | 写了 `map`/`filter` 却什么都没发生，甚至以为副作用被执行了 |
| 为什么 | 适配器只构建迭代器，必须被消费（`collect`/`for`/`sum`/`count`）才逐个求值 |
| 规避 | 记得收尾；需要立即执行就用 `for_each` 或 `for` |

```rust
fn main() {
    let v = vec![1, 2, 3];
    let lazy = v.iter().map(|x| x * 2); // 这一步什么都没算
    let doubled: Vec<i32> = lazy.collect(); // 到这里才真正执行
    println!("{:?}", doubled);
}
```

## 5. clone 滥用：把借用问题变成性能问题

| 项目 | 内容 |
| --- | --- |
| 现象 | 处处 `.clone()` 让借用检查通过了，但热路径上全是堆分配 |
| 为什么 | `clone` 绕过了借用检查而不是解决问题，`String`/`Vec` 的拷贝是 O(n) |
| 规避 | 参数先用 `&T`/`&str`/`&[T]`，只在确实需要所有权时克隆 |

```rust
fn total_len(items: &[String]) -> usize {
    items.iter().map(|s| s.len()).sum()
}

fn main() {
    let items = vec![String::from("ab"), String::from("cde")];
    println!("{}", total_len(&items)); // 借用即可
    println!("{}", items.len()); // 调用后 items 仍可用
}
```

## 6. `&str` 与 `String` 混用

| 项目 | 内容 |
| --- | --- |
| 现象 | 函数签名写 `String` 后，传字面量要 `to_string()`；返回 `&str` 又报生命周期错 |
| 为什么 | `&str` 是借用视图，`String` 是拥有所有权的缓冲区，二者不能互相赋值 |
| 规避 | 入参用 `&str`（或 `impl AsRef<str>`），出参需要新数据就用 `String` |

```rust
fn greet(name: &str) -> String {
    format!("hi, {name}")
}

fn main() {
    let owned = String::from("rust");
    println!("{}", greet(&owned)); // &String 自动解引用为 &str
    println!("{}", greet("world")); // 字面量本身就是 &'static str
}
```

## 7. `RefCell`：把编译期借用检查推迟到运行时

| 项目 | 内容 |
| --- | --- |
| 现象 | `already borrowed: BorrowMutError` 运行时 panic |
| 为什么 | `borrow_mut()` 在已有 `borrow()` 存活时直接 panic，没有编译期提示 |
| 规避 | 让 `RefCell` 的借用范围尽量短，别把 `Ref` 跨函数长期持有 |

```rust
use std::cell::RefCell;

fn main() {
    let cell = RefCell::new(1);
    {
        let r = cell.borrow();
        println!("{}", *r);
    } // 借用在这里归还
    *cell.borrow_mut() += 1;
    println!("{}", cell.borrow());
}
```

## 8. `Mutex` 死锁：同一线程重复加锁

| 项目 | 内容 |
| --- | --- |
| 现象 | 程序卡住不动，没有 panic 也没有输出 |
| 为什么 | `std::sync::Mutex` 不可重入，同一线程二次 `lock()` 会永久等待自己 |
| 规避 | 一把锁只加一次，需要嵌套就一次性取出所需数据；用 `try_lock` 兜底 |

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(0);
    {
        let mut g = m.lock().unwrap();
        *g += 1;
        println!("{}", *g);
    } // guard 在这里释放
    // 之后再 lock 才不会死锁
    println!("{}", *m.lock().unwrap());
}
```

## 9. 跨 `await` 持锁

| 项目 | 内容 |
| --- | --- |
| 现象 | 异步服务吞吐骤降，甚至整条链路卡死；`tokio::spawn` 报 future 不是 `Send` |
| 为什么 | `MutexGuard` 不是 `Send`，跨越 `.await` 会让整个 future 不可跨线程调度 |
| 规避 | 只在同步小块内持锁，取完数据立刻 `drop(guard)`，别把 `.await` 写在锁里 |

```text
// ❌ guard 活过了 await
let guard = state.lock().await;
let data = fetch(&guard.url).await;
guard.count += 1;

// ✅ 先取出需要的数据，释放锁，再 await
let url = { state.lock().await.url.clone() };
let data = fetch(&url).await;
{ state.lock().await.count += 1; }
```

## 10. Drop 顺序：局部变量逆序析构

| 项目 | 内容 |
| --- | --- |
| 现象 | 以为先声明的先释放，结果日志顺序反了 |
| 为什么 | 同一作用域内局部变量按**声明顺序的逆序**析构 |
| 规避 | 有依赖关系的资源用显式块或 `drop()` 控制生命周期 |

```rust
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn main() {
    let _a = Noisy("a"); // 最后析构
    let _b = Noisy("b"); // 先析构，输出 b 再 a
    println!("end of main");
}
```

## 11. `as` 转换会静默截断

| 项目 | 内容 |
| --- | --- |
| 现象 | `300u32 as u8` 得到 44，`-1i32 as u32` 得到 4294967295，都不报错 |
| 为什么 | `as` 是原生数值转换，只保留低位或重新解释符号位 |
| 规避 | 用 `try_into()` 显式处理越界，或先 `checked_*` 校验范围 |

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let big: u32 = 300;
    println!("{}", big as u8); // 44，静默截断
    let small: u8 = big.try_into()?; // 这里会返回 Err，不会悄悄出错
    println!("{}", small);
    Ok(())
}
```

## 12. `HashMap` 的哈希是随机的

| 项目 | 内容 |
| --- | --- |
| 现象 | 遍历顺序每次运行都不同，测试里断言顺序会随机挂 |
| 为什么 | 默认用 `RandomState` 种子，防止哈希碰撞攻击，代价是顺序不保证 |
| 规避 | 要稳定顺序就排序输出或改用 `BTreeMap`，测试别断言迭代顺序 |

```rust
use std::collections::HashMap;

fn main() {
    let mut m = HashMap::new();
    m.insert("b", 2);
    m.insert("a", 1);
    let mut keys: Vec<&str> = m.keys().copied().collect();
    keys.sort(); // 自己排序才稳定
    for k in keys {
        println!("{} = {}", k, m[k]);
    }
}
```

## 13. `Vec` 扩容会让旧引用失效

| 项目 | 内容 |
| --- | --- |
| 现象 | 拿着 `&v[0]` 再 `v.push(x)`，编译报 `cannot borrow as mutable` |
| 为什么 | 扩容可能重新分配内存，旧引用会悬垂；借用检查在编译期就拦住 |
| 规避 | 需要引用就重新取；提前 `with_capacity` 减少扩容但**不能**绕过借用检查 |

最小复现：

```text
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
    let first = &v[0];
    v.push(4);                   // ❌ 扩容后 first 可能悬垂
    println!("{}", first);
```

修复：

```rust
fn main() {
    let mut v = Vec::with_capacity(8); // 减少扩容次数
    v.extend([1, 2, 3]);
    let first = v[0]; // 值类型直接拷贝出来
    v.push(first + 10);
    println!("{:?}", v);
}
```

## 14. 闭包捕获：`move` 与借用范围

| 项目 | 内容 |
| --- | --- |
| 现象 | 闭包还在作用域内时无法使用被捕获的变量；线程里必须加 `move` |
| 为什么 | 闭包按 `Fn`/`FnMut`/`FnOnce` 自动选择借用方式，捕获会一直持续到闭包最后一次使用 |
| 规避 | 缩小闭包存活范围，需要转移给线程就用 `move` + `clone` 句柄 |

```rust
fn main() {
    let mut count = 0;
    {
        let mut inc = || {
            count += 1;
            count
        };
        println!("{}", inc());
    } // 闭包在这里释放，&mut count 归还
    println!("{}", count);
}
```

## 15. `Send` / `Sync` 误判

| 项目 | 内容 |
| --- | --- |
| 现象 | 把 `Rc`/`RefCell` 塞进 `thread::spawn` 或 `tokio::spawn` 直接编译失败 |
| 为什么 | `Rc` 的引用计数不是原子的，`RefCell` 不是线程安全的，二者都不是 `Send` |
| 规避 | 跨线程共享数据用 `Arc<Mutex<T>>` 或 `Arc<RwLock<T>>`；`Rc` 只留在单线程 |

最小复现：

```text
error[E0277]: `Rc<i32>` cannot be sent between threads safely
    let a = Rc::new(1);
    thread::spawn(move || println!("{}", a));   // ❌ Rc 不是 Send
```

修复：

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let a = Arc::new(1);
    let b = Arc::clone(&a);
    let h = thread::spawn(move || println!("子线程看到 {}", b));
    h.join().unwrap();
    println!("主线程看到 {}", a);
}
```
